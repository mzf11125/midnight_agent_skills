# Midnight Verify

A multi-method verification framework for Midnight Network contracts. This skill covers the complete verification lifecycle from extracting claims to collecting evidence and producing structured reports.

## Verification Overview

The verification framework provides a systematic approach to validating Midnight contracts. It combines seven distinct verification methods that each focus on a different aspect of contract correctness. The framework is designed to be composable so that individual methods can be used in isolation or combined for comprehensive coverage.

The core philosophy is that no single verification technique is sufficient for proving the correctness of a zero-knowledge contract. Compile verification confirms syntactic validity. Runtime execution validates behavior. Type checking prevents logic errors. Source inspection detects privacy leaks. End-to-end testing validates the full lifecycle. Together these methods form a robust verification pipeline.

The verification workflow follows a structured process. First claims are extracted from contract documentation and source code. Then appropriate verification methods are selected based on the claim type. Evidence is collected from each method execution. Results are aggregated and reported in a standardized format.

### Verification Methods

There are seven core verification methods available for Midnight contracts.

**compile** runs the `compactc` compiler on the contract source. It confirms that the contract compiles successfully and produces valid ZKIR output. This method catches syntax errors, type mismatches, and compilation failures.

**execute** runs the contract in the Compact TypeScript runtime environment. It validates transaction execution, state transitions, and function return values against expected outcomes.

**typecheck** validates the type system of the contract. It checks that all types are correct, that type constraints are satisfied, and that the type system is internally consistent.

**inspect** performs static analysis on contract source code. It audits disclosures, detects potential privacy leaks, checks state access patterns, and analyzes circuit complexity.

**e2e** runs full end-to-end tests using the testkit-js environment. It covers the complete deploy and call cycle across multiple networks.

**state** verifies contract state directly. It reads on-chain state and compares it against expected values using hash comparison and structural equality checks.

**proving** validates proof generation and verification. It checks that proofs can be generated and verified correctly and that verifier keys are managed properly.

## Compile Verification

Compile verification ensures that the contract source code is syntactically valid and can be successfully compiled into ZKIR format. This is the most fundamental verification step and should be performed before any other verification method.

### compactc Compilation

The `compactc` compiler transforms Compact source code into ZKIR intermediate representation. A successful compilation produces three key artifacts: a ZKIR file, a verifier key, and circuit size metrics. The compilation process validates syntax, resolves imports, performs type checking, and generates the circuit representation.

```typescript
import { verify, compileMethod } from "midnight-verify";

const result = await verify.compile({
  source: "path/to/contract/src",
  method: compileMethod.compactc,
  network: "local"
});
```

A compile verification confirms several properties. The contract source is syntactically valid. All imports resolve correctly. No type errors exist in the source. The ZKIR output file is generated. The verifier key is produced correctly. Circuit size is within acceptable bounds.

### ZKIR Output Validation

After compilation the ZKIR output should be validated for correctness. The ZKIR file must be non-empty and parseable. It must contain all expected circuit definitions. Each circuit must have a valid structure with inputs, outputs, and internal operations. The ZKIR byte size should be within expected ranges for the contract complexity.

### Verifier Key Generation

The verifier key is a cryptographic artifact that allows anyone to verify proofs generated by the contract. Compile verification checks that the verifier key is generated and has the correct format. The key must be a valid byte sequence. It must be consistent with the contract source. It must be usable for proof verification.

### Prover Key Verification

The prover key is used by proof servers to generate proofs for transactions. Compile verification checks that the prover key is generated correctly. The key must match the contract specification. It must produce valid proofs when used by the proof server.

### Circuit Size Checks

Each circuit in the contract has a size measured in constraints. Compile verification reports these sizes and checks them against expected thresholds. Circuits that exceed size limits may be too expensive to prove or may indicate overly complex logic that should be simplified.

## Execute Verification

Execute verification runs the contract through actual execution in the Compact TypeScript runtime. This method validates that the contract behaves correctly when called with specific inputs.

### runProgram

The `runProgram` function executes a contract in the runtime environment. It takes a contract definition, a circuit name, and input arguments and produces execution results. This function simulates what happens when a transaction calls the contract on the network.

```typescript
const result = await verify.execute({
  contract: "Counter",
  circuit: "increment",
  inputs: { amount: 5 },
  method: executeMethod.runProgram
});
```

### VmResults

The `VmResults` object contains the output of contract execution. It includes the return value, the new state after execution, any events emitted, and the execution trace. Each of these components can be verified independently.

The return value must match the expected output for the given inputs. The new state must reflect the correct state transitions. Events must be emitted in the expected order with the expected data. The execution trace shows the sequence of operations performed.

### VmStack

The `VmStack` represents the internal state of the virtual machine during execution. It can be inspected to verify that intermediate values are correct, that the stack does not overflow, and that memory usage stays within bounds.

### Transaction Simulation

Transaction simulation runs a contract call as if it were a real transaction on the network but without actually submitting it. This allows verification of the full transaction lifecycle including fee estimation, signature verification, and state transitions.

### State Transition Validation

Each circuit in a contract defines how ledger state changes. Execute verification checks that state transitions are correct. The state before the call must match the expected starting state. The state after the call must match the expected ending state. The delta between before and after must correspond to the effect of the circuit.

## Type Check Verification

Type check verification validates the type system of the contract source code. Midnight contracts benefit from strong static typing and type errors caught early prevent runtime failures.

### Type System Validation

The type system validation checks that all types in the contract are well-formed. Ledger types must be valid state types. Function parameter types must be valid input types. Function return types must be valid output types. Witness types must be valid private data types. All type variables must be properly bounded.

### Type Error Detection

Common type errors that this verification catches include assigning a value of the wrong type, passing the wrong number of arguments, using a variable that does not exist, calling a function that does not exist, and type parameter mismatches in generic types.

### CompactType Checks

The `CompactType` system includes several built-in types that each have specific rules. `Bytes<N>` types must have a known size at compile time. `Uint<N>` types must have valid bit widths. `Boolean` types can only be assigned true or false. `List<T>` types must have consistent element types. `Struct` types must have all fields properly declared.

### Descriptor Validation

Contract descriptors define the public interface of a contract. Type check verification validates that descriptors match the contract implementation. Each circuit listed in the descriptor must exist in the contract. Circuit parameter types must match the descriptor. Return types must be consistent.

## Inspect Source

Source inspection performs static analysis on contract source code to detect potential issues that compilation alone cannot catch. This method focuses on privacy guarantees, disclosure patterns, and circuit complexity.

### Contract Source Analysis

The source analyzer reads the contract source and builds an abstract representation of its structure. It identifies all ledgers, circuits, witnesses, and supporting functions. It maps the relationships between these components. It traces data flow from witnesses through circuits to ledgers and disclosures.

### Disclosure Audit

Every value that leaves the contract becomes public on the blockchain. The disclosure audit examines every `disclose()` call in the contract and verifies that only appropriate data is being disclosed. It checks that disclosures are intentional and that no sensitive data is inadvertently exposed.

The audit flags potential issues such as disclosing witness-derived data without proper masking, disclosing intermediate computation values, and disclosing data that could be used to link multiple transactions. Each flagged item includes a severity rating and a suggested remediation.

### Privacy Leak Detection

Privacy leak detection goes beyond explicit disclosure checks. It examines the contract for potential information leaks through side channels. For example if a circuit takes different code paths based on private data the execution trace may leak information about that data. The detector also checks for timing-based leaks and data-dependent memory access patterns.

### State Access Patterns

Every circuit in a Midnight contract declares which ledger states it reads and which it writes. The state access analyzer verifies that these declarations are correct. A circuit that reads state without declaring it may cause proofs to fail. A circuit that writes state without proper authorization may be rejected by the network.

### Circuit Complexity Analysis

Complex circuits are more expensive to prove and more likely to contain bugs. The complexity analyzer measures the size of each circuit in terms of constraints and reports which circuits exceed recommended thresholds. It also identifies overly complex circuits that should be split into simpler components.

## End-to-End Testing

End-to-end testing verifies the complete lifecycle of a contract from deployment through multiple transactions. This method uses the testkit-js environment to simulate a full network experience.

### Full Deploy and Call Cycle

The e2e test deploys a contract to a local test network and then calls its circuits. It validates that the deployment transaction succeeds, that the contract address is assigned correctly, that circuit calls produce correct results, and that state is updated correctly across multiple calls.

```typescript
const result = await verify.e2e({
  contract: "Counter",
  testCases: [
    { circuit: "increment", inputs: [1] },
    { circuit: "getCount", expectedResult: 1 },
    { circuit: "decrement", inputs: [1] },
    { circuit: "getCount", expectedResult: 0 }
  ],
  network: "local"
});
```

### Testkit-js Environment

The testkit-js environment provides a complete Midnight development environment for testing. It includes a local ledger, proof server, wallet implementations, and transaction submission. The environment is configured to match production behavior as closely as possible while running entirely on the local machine.

### Multi-Network Testing

Contracts should be tested on all target networks before deployment. Multi-network testing validates that the contract behaves correctly on local devnet, preprod network, and preview network. Each network may have different configuration parameters and the contract must handle these differences correctly.

### Transaction Lifecycle Validation

The transaction lifecycle includes several phases: transaction construction, proof generation, network submission, block inclusion, and state finalization. E2e testing validates each phase independently and as part of the complete flow. It checks that transactions are not lost, that proofs are valid, that blocks include the expected transactions, and that state reaches finality within the expected time window.

## Verification Methods

The verification framework supports multiple execution environments for running verification methods. Each environment has different capabilities and trade-offs.

### Node.js Runtime

The compile method runs in a Node.js runtime environment. It spawns the `compactc` compiler as a child process and captures its output. The runtime provides access to the file system for reading contract sources and writing verification artifacts. It runs independently of any network connection.

### Compact TypeScript Environment

The execute method runs in the Compact TypeScript runtime. This environment provides a full implementation of the Midnight virtual machine including the ledger, proof verification, and transaction processing. It executes contracts exactly as they would run on the network but entirely in-process for fast verification.

### Proof Server

The proving method communicates with a proof server. The proof server accepts contracts and inputs and generates proofs. It must be running and accessible before proving verification can be performed. The proof server can run locally for testing or connect to remote servers for preprod and preview network verification.

### Devnet Deployment

The e2e method deploys contracts to a local devnet. The devnet runs a full Midnight node stack including the ledger, consensus, and indexer. Contracts deployed to devnet behave identically to production contracts. Devnet provides the most realistic testing environment.

## Claim Types for Verification

Verification always starts with claims. A claim is a specific statement about contract behavior that can be verified as true or false. Claims are categorized by the type of property they assert.

### Function Return Types

Claims about function return values assert that a circuit returns a specific value for given inputs. For example a claim might state that `getCount()` returns `5` after `increment(5)` is called. These claims are verified using the execute and e2e methods.

### State Behavior

Claims about state behavior assert how ledger state changes in response to circuit calls. For example a claim might state that the counter state increases by exactly the amount passed to the increment circuit. These claims are verified using the state and execute methods.

### Transaction Outcomes

Claims about transaction outcomes assert whether a transaction succeeds or fails. For example a claim might state that calling a circuit with an unauthorized witness causes the transaction to fail. These claims are verified using the e2e method.

### Privacy Guarantees

Claims about privacy assert what data is public and what is private. For example a claim might state that the balance of a specific participant is never disclosed on chain. These claims are verified using the inspect method.

### Gas Costs

Claims about gas costs assert the computational cost of executing a circuit. These claims are verified using the execute method which reports gas consumption for each circuit call.

### Error Conditions

Claims about error conditions assert that specific errors are raised under specific conditions. For example a claim might state that calling a circuit with invalid parameters raises a `TypeError`. These claims are verified using the execute method with error validation enabled.

## Structured Verification

The verification framework follows a structured workflow that ensures verification is systematic, reproducible, and auditable.

### Claim Extraction from Documentation

The first step in structured verification is extracting claims from contract documentation. Documentation typically states what a contract does and these statements become verification claims. Each claim is assigned a unique identifier and categorized by type.

### Method Selection

For each claim the framework selects the appropriate verification method based on the claim type. Function return claims use execute verification. State behavior claims use state verification. Privacy guarantees use inspect verification. The selection process is automated based on claim type to method mappings.

### Evidence Collection

As each verification method runs it collects evidence in the form of execution logs, state snapshots, and test results. Evidence is timestamped and associated with the claim it supports. All evidence is stored in a structured format for later review.

### Result Reporting

Verification results are reported in a standardized format. Each claim gets a pass, fail, or inconclusive result. Failed claims include details about what went wrong including expected versus actual values. The report aggregates results across all claims and provides a summary of verification coverage.

## ContractState Verification

Contract state is the persistent data that contracts maintain on the Midnight blockchain. Verifying contract state ensures that the on-chain state matches expectations.

### verifyContractState

The `verifyContractState` function reads the current state of a deployed contract and compares it against expected values. It can verify individual state fields or the complete state. The comparison uses structural equality meaning that two states are equal if they have the same structure and the same values in all fields.

```typescript
const result = await verify.state({
  contract: "Counter",
  expectedState: {
    count: 42,
    owner: "0x1234..."
  },
  method: stateMethod.verifyContractState
});
```

### getStates

The `getStates` function reads all states of a contract including both public and private states that the caller has access to. It returns a complete snapshot of the contract state at the current block.

```typescript
const states = await verify.getStates({
  contract: "Counter",
  network: "local"
});
```

### getPublicStates

The `getPublicStates` function reads only the public states of a contract. Public states are visible to all network participants. This function is useful for verifying that only appropriate data is public and that no private data leaks onto the public ledger.

### State Hash Comparison

Contract state hashes provide a compact representation of the complete state. Two states are equivalent if and only if their hashes are equal. The hash comparison method is faster than structural comparison and is suitable for regression testing where the same inputs should produce the same state hash every time.

## Transaction Verification

Transaction verification ensures that transactions are constructed correctly and produce the expected outcomes.

### expectSuccessfulCallTx

This helper validates that a call transaction succeeds. It constructs a call transaction, submits it to the network, and checks that the transaction result indicates success. If the transaction fails the verification fails with details about the error.

```typescript
const tx = await verify.expectSuccessfulCallTx({
  contract: "Counter",
  circuit: "increment",
  inputs: { amount: 1 },
  network: "local"
});
```

### expectSuccessfulDeployTx

This helper validates that a deploy transaction succeeds. It constructs a deploy transaction, submits it to the network, and checks that the contract is deployed at the expected address. It also verifies that the initial state matches the expected initial values.

```typescript
const tx = await verify.expectSuccessfulDeployTx({
  contract: "Counter",
  network: "local"
});
```

### expectSuccessfulTxData

This helper validates the data within a successful transaction. It checks that the transaction data matches expected values including the circuit called, the inputs provided, and the outputs produced. It works for any transaction type including deploy, call, and maintenance transactions.

### txsEqual

The `txsEqual` function compares two transactions for equality. Transactions are equal if they have the same type, the same contract address, the same circuit, the same inputs, and produce the same outputs. This function is useful for verifying that two different paths produce the same transaction.

### stateValueEqual

The `stateValueEqual` function compares two state values for structural equality. It handles complex state types including nested structures, lists, and maps. It performs deep comparison ensuring that all fields and subfields match.

## expectFoundAndDeployed Helpers

These helpers combine finding a deployed contract and performing verification in a single operation. They are designed for common testing patterns where a contract is first deployed and then verified.

### expectFoundAndDeployedStatesEqual

This helper finds a deployed contract and verifies that its states match expected values. It queries the indexer for the contract, validates that the contract exists, reads its states, and compares them against expectations.

```typescript
const result = await verify.expectFoundAndDeployedStatesEqual({
  contractName: "Counter",
  expectedStates: {
    count: 0,
    owner: wallet.address
  },
  network: "local"
});
```

### expectFoundAndDeployedTxDataEqual

This helper finds a deployed contract and verifies that the data from calling its circuits matches expectations. It calls each circuit, collects the transaction data, and compares against expected data values.

### expectFoundAndDeployedTxPrivateDataEqual

This helper focuses on private transaction data. It verifies that the private data within transactions matches expectations such as private state changes that should not be visible on the public ledger.

### expectFoundAndDeployedTxPublicDataEqual

This helper focuses on public transaction data. It verifies that the public data within transactions matches expectations including events emitted, public state changes, and disclosed values.

## Proving Verification

Proving verification ensures that the zero-knowledge proof system works correctly for the contract. This is critical because incorrect proofs would allow invalid state transitions.

### Proof Generation

Proof generation is the process of creating a zero-knowledge proof that a transaction is valid. The proving verification checks that proofs can be generated for all circuits in the contract. It also checks that proof generation terminates within the expected time limit and produces proofs of the expected size.

```typescript
const result = await verify.proving({
  contract: "Counter",
  circuit: "increment",
  inputs: { amount: 1 },
  method: provingMethod.generate
});
```

### Proof Validation

Proof validation checks that generated proofs are actually valid. A valid proof demonstrates that the circuit was executed correctly without revealing the private inputs. The verification ensures that valid proofs pass verification and that invalid proofs are rejected.

### Verifier Key Insertion

The verifier key must be inserted into the proof server before proofs can be verified. The insertion verification checks that the key insertion transaction succeeds and that the key is properly registered with the proof server.

```typescript
const result = await verify.proving({
  contract: "Counter",
  method: provingMethod.insertVerifierKey
});
```

### Verifier Key Removal

When a contract is upgraded or replaced its verifier key may need to be removed. The removal verification checks that the key removal transaction succeeds and that the key is no longer registered with the proof server.

### verifierKeysEqual

The `verifierKeysEqual` function compares two verifier keys for equality. Keys are equal if they have the same byte representation. This function is useful for verifying that the verifier key on the proof server matches the verifier key generated during compilation.

## Maintenance Verification

Maintenance verification covers the administrative operations of a contract including maintenance authority management and verifier key lifecycle.

### ContractMaintenanceAuthority

Every Midnight contract has a maintenance authority that can perform administrative operations on the contract. Maintenance verification checks that the maintenance authority is correctly identified and that only authorized parties can perform maintenance operations.

### ReplaceAuthority

The `ReplaceAuthority` operation transfers maintenance authority from one party to another. Maintenance verification checks that this operation works correctly. The old authority must sign the replacement transaction. After replacement the new authority must be able to perform maintenance operations. The old authority must no longer be able to perform maintenance operations.

### Verifier Key Lifecycle

The verifier key has a complete lifecycle from generation through activation to retirement. Maintenance verification checks each phase of this lifecycle. Key generation must produce a valid key. Key insertion must register the key with the proof server. Key activation must allow proofs to be verified. Key retirement must prevent new proofs from being verified. Key replacement must transition cleanly from old key to new key.

### Authority Checks

Maintenance verification includes comprehensive authority checks. Unauthorized parties must not be able to perform maintenance operations. Attempted unauthorized operations must be rejected with appropriate error codes. The maintenance authority must be able to prove its authorization through valid signatures.

## Error Verification

Error verification ensures that contracts fail correctly when given invalid inputs or when operating under error conditions. Proper error handling is as important as correct successful operation.

### Expected Errors

Expected errors are errors that the contract is designed to raise under specific conditions. Error verification checks that these errors are raised when the triggering conditions are met. For example a circuit that requires a specific witness should raise an error when called with an invalid witness.

```typescript
const result = await verify.error({
  contract: "Counter",
  circuit: "increment",
  inputs: { amount: -1 },
  expectedError: "CounterUnderflow",
  method: errorMethod.expected
});
```

### Error Code Validation

Each error has a specific error code that identifies it on the network. Error verification validates that the correct error code is produced for each error condition. It checks the error type, error message, and error data against expectations.

### Transaction Rejection Patterns

The network rejects invalid transactions before they are included in a block. Error verification validates the rejection patterns for different types of invalid transactions. It checks that the rejection occurs at the correct phase of transaction processing and that the rejection reason is correctly communicated.

### Partial Success Handling

Some transactions may partially succeed and partially fail. Error verification checks that partial success is handled correctly. State changes from successful parts of the transaction should be applied. State changes from failed parts should be rolled back. The transaction result should correctly indicate which parts succeeded and which failed.

## Multi-Network Verification

Midnight Network operates across multiple networks with different configurations. Multi-network verification ensures that contracts work correctly on all target networks.

### Local Devnet Testing

Local devnet provides the fastest feedback cycle for verification. Contracts are deployed and tested on a local Midnight node stack. Local devnet uses the same software as production but runs entirely on the developer machine. All verification methods are available on local devnet.

### Preprod Validation

The preprod network is a shared test network that mimics the production environment. Contracts should be verified on preprod before promotion to mainnet. Preprod validation catches configuration differences and network-specific behavior that might not appear on local devnet.

### Preview Checks

The preview network runs upcoming protocol changes before they reach mainnet. Contracts should be verified on preview to ensure compatibility with future protocol versions. This is especially important when the Midnight protocol undergoes upgrades that affect contract behavior.

### Mainnet Readiness

Mainnet readiness checks validate that a contract is safe for production deployment. All verification methods must pass on all test networks. All claims must be verified. All error conditions must be handled. The verification report must indicate full readiness before mainnet deployment proceeds.

## Verification Reports

Verification reports communicate verification results to developers, reviewers, and automated systems.

### Pass/Fail Results

Each claim is reported as pass, fail, or inconclusive. A pass means the claim was verified successfully. A fail means the claim was falsified. An inconclusive result means the verification could not determine the truth of the claim typically due to environmental issues or missing prerequisites.

### Evidence Collection

Each verification run collects evidence to support the results. Evidence includes execution logs, state snapshots, transaction data, proof artifacts, and error traces. Evidence is preserved with timestamps and unique identifiers for traceability.

### Screenshot Capture

For UI verification screenshots are captured to provide visual evidence of correct behavior. Screenshots are annotated with the claim being verified and the timestamp of capture. They are included in the verification report as inline images.

### Log Analysis

Verification logs are analyzed to extract relevant information. The analyzer identifies key events, timing information, error messages, and warnings. It correlates log events with claims and highlights discrepancies.

### Structured Output

Verification reports are produced in a structured format that can be consumed by other tools. The format includes JSON for programmatic consumption, Markdown for human readability, and CI annotations for automated pipeline integration. Each format contains the same information presented in the appropriate style.

## CI Integration

Verification should be integrated into continuous integration pipelines to provide automated quality gates.

### Automated Verification in CI Pipelines

CI pipelines run verification automatically on every code change. The pipeline triggers verification when contracts are modified. It runs the appropriate verification methods based on the scope of changes. It fails the pipeline if verification fails.

### Regression Testing

Verification serves as a regression testing suite for contracts. Claims that previously passed must continue to pass after code changes. The CI pipeline maintains a history of verification results and flags regressions for immediate attention.

### PR Gates

Pull request gates prevent merging changes that break verification. The gate checks that all required verification methods pass before allowing the merge. Gates can be configured with minimum pass thresholds and required method coverage.

### Scheduled Verification

Scheduled verification runs on a regular cadence even when no code changes have been made. This catches regressions caused by external factors such as network upgrades, proof server changes, or dependency updates. Scheduled runs are typically configured to run daily on all target networks.

## Verification Agents

The verification framework includes specialized agents for different verification domains. Each agent focuses on a specific aspect of verification and produces results in a standardized format.

There are seven agent types corresponding to the seven verification methods. The compile agent handles compile verification. The execute agent handles runtime verification. The type agent handles type checking. The inspect agent handles source analysis. The e2e agent handles end-to-end testing. The state agent handles state verification. The proving agent handles proof verification.

### Agent Coordination

A coordinator agent manages the execution of verification agents. It receives claims from the claim extractor, assigns claims to appropriate agents, collects results from each agent, and produces the aggregated verification report. The coordinator can run agents in parallel for efficiency.

### Result Aggregation

Results from multiple agents are aggregated into a unified verification report. Conflicting results from different agents are flagged for manual review. The aggregation process prioritizes results from the most authoritative agent for each claim type and provides a confidence score for each aggregated result.

## Best Practices

### Comprehensive Claim Coverage

Claims should cover all aspects of contract behavior. Every circuit should have claims for success cases and error cases. Every state transition should be claimed. Every disclosure should be audited. Comprehensive claim coverage ensures that no behavior goes unverified.

### Deterministic Verification

Verification must be deterministic. Running the same verification on the same contract with the same inputs must produce the same results every time. Nondeterministic tests undermine confidence in the verification process and make regression detection unreliable.

### Reproducible Results

Verification results must be reproducible by anyone with access to the contract source and the verification configuration. All dependencies including network versions, compiler versions, and prover versions must be pinned. Reproducibility ensures that verification results can be independently validated.

### Evidence Preservation

All verification evidence must be preserved for future reference. Evidence should be stored in a versioned artifact repository. It should be associated with the specific version of the contract it verifies. Evidence preservation supports audit requirements and facilitates debugging of issues discovered later.
