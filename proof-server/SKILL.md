# Proof Server

## Proof Server Overview

The Midnight proof server generates zero-knowledge proofs for Compact contract calls and deployments. Every transaction on Midnight that involves a Compact contract must include a valid ZK proof. The proof server creates these proofs using the contract's compiled ZKIR (Zero-Knowledge Intermediate Representation) artifacts and the user's witness data.

The proof server performs three critical functions in the Midnight ecosystem. First it generates ZK proofs from witness data and the contract's circuit definition. Second it manages proving keys including versioning, distribution, and rotation. Third it handles verifier key distribution so that proofs generated by the server can be verified by the network.

Zero-knowledge proofs allow the Midnight network to verify that a contract execution was valid without revealing the private inputs used in that execution. The proof server is responsible for translating private witness data into a cryptographic proof that attests to the correct execution of the Compact circuit.

Proving key management is essential for security. Each version of a Compact contract has a corresponding proving key and verifier key pair. The proving key is used by the proof server to generate proofs. The verifier key is published on-chain so that validators and other participants can verify proofs. Key versioning ensures that proofs generated with old keys are rejected after a contract upgrade.

Verifier key distribution is handled by the proof server. When a dApp submits a transaction, it includes the verifier key hash that the proof was created against. The network checks that this hash matches the on-chain verifier key for the contract version being called. If the hashes do not match, the transaction is rejected.

## Internal Architecture

### Proof Generation Pipeline

The proof generation pipeline consists of several stages. Stage one is witness processing. The proof server receives witness data from the dApp and validates that it matches the expected input types defined by the contract's circuit. Stage two is circuit execution. The proof server loads the ZKIR artifact for the contract and evaluates the circuit with the provided witness data. Stage three is proof serialization. The output of circuit evaluation is a cryptographic proof that is serialized into the format expected by the Midnight ledger.

Witness processing validates input types, checks that all required witnesses are provided, normalizes witness values to the circuit's expected format, and flagging any missing or invalid witnesses with clear error messages. This stage catches configuration errors before the expensive circuit execution begins.

Circuit execution involves loading the ZKIR artifact which is a pre-compiled representation of the Compact contract's circuit. The artifact is loaded from the proof server's key store or from a remote repository. The circuit is then evaluated with the witness data. This evaluation is computationally expensive and may take several seconds to minutes depending on the contract's complexity.

Proof serialization converts the internal proof representation into the binary format that the Midnight ledger expects. This format is compact and includes the proof data, the public inputs, and metadata about the proving key version. The serialized proof is returned to the dApp for inclusion in the transaction.

### Witness Processing

Witness data comes from the dApp's interaction with the user. When a user wants to call a contract method, the dApp collects the private inputs from the user's wallet. These inputs include things like account balances, secret values, and any other data that should remain private.

The witness data is structured according to the contract's circuit definition. Each input parameter in the circuit corresponds to a witness value. The proof server validates that the witness structure matches the expected circuit inputs and that all required values are present.

### Circuit Execution

The ZKIR (Zero-Knowledge Intermediate Representation) is a compiled form of the Compact contract's circuit. It is produced by the Compact compiler and contains the arithmetic circuit description, the constraint system, and metadata about input and output types. The proof server loads the ZKIR for the specific contract version being called.

Circuit evaluation solves the constraint system defined by the ZKIR. The output is a proof that the constraints are satisfied and a set of public outputs that are revealed on-chain. The complexity of the circuit determines the proving time. Simple circuits may prove in under a second while complex circuits with many constraints may take minutes.

### Proof Serialization

The serialized proof format includes the proof binary data, the public inputs for on-chain verification, the verifier key hash for key version matching, and metadata about the proof server version. This format is standardized across all proof server implementations and supported by the Midnight ledger.

## API Reference

### Proof Generation Endpoints

The primary endpoint for proof generation is the proof endpoint. This endpoint accepts a proof payload containing the contract address, method name, witness data, and the contract's ZKIR artifact. The endpoint returns a serialized proof that can be included in a transaction.

When generating a proof for a contract call, the endpoint requires the contract address so the proof server can look up the correct ZKIR artifact, the method name being called on the contract, the witness data containing the private inputs, and optionally a callback URL for asynchronous proof generation.

The response includes the serialized proof as a hex-encoded string, the public inputs extracted from the proof, the verifier key hash, and a proof ID for tracking and debugging.

### Check Endpoints

The check endpoint verifies the status of the proof server. It returns information about the server's health, the loaded key material, and the server's configuration. This endpoint is used by dApps and monitoring systems to ensure the proof server is operational before attempting proof generation.

The check response includes the server version, the list of loaded contracts and their key versions, the server's uptime, and the current proof generation queue depth.

### Status Endpoints

The status endpoint provides detailed information about ongoing proof generation operations. It accepts a proof ID and returns the current status of that proof request. Status values include queued meaning the proof is waiting for resources, in progress meaning the proof is being generated, completed meaning the proof is ready, and failed meaning the proof generation encountered an error.

### Configuration Endpoints

The configuration endpoint returns the proof server's current configuration. This includes the server URL, timeout settings, key material paths, logging configuration, and resource limits. Some configuration values can be updated at runtime through this endpoint.

## Proving Payloads

### createProvingPayload

The `createProvingPayload` function creates a payload for a standard proof generation request. It takes the contract address, the method name being called, and the witness data. It returns a structured payload that can be sent to the proof server.

```typescript
const payload = createProvingPayload({
  contractAddress: "contract_abc...",
  methodName: "transfer",
  witness: witnessData
})
```

### createProvingTransactionPayload

The `createProvingTransactionPayload` function creates a payload specifically for transaction-level proof generation. This includes additional transaction metadata that the proof server needs to generate the correct proof. It takes the contract address, method name, witness data, and transaction context.

```typescript
const payload = createProvingTransactionPayload({
  contractAddress: "contract_abc...",
  methodName: "transfer",
  witness: witnessData,
  txContext: { nonce: 5, feeAddress: "addr_..." }
})
```

### createCheckPayload

The `createCheckPayload` function creates a payload for checking the status of a previously submitted proof request. It takes the proof ID returned by the proof generation request.

```typescript
const checkPayload = createCheckPayload({
  proofId: "proof_abc..."
})
```

## Proof Types

### Proof

The `Proof` type represents a completed zero-knowledge proof. It contains the serialized proof data in binary format, the public inputs that are revealed on-chain, the verifier key hash for verification, and metadata about the proof generation including timing and resource usage.

### PreProof

The `PreProof` type represents a proof that is still in generation. It contains the proof ID for status tracking, the current status of generation, and estimated completion time. This type is returned when proof generation is asynchronous and the proof is not yet ready.

### NoProof

The `NoProof` type represents a proof-less operation. Some contract methods do not require a proof, such as methods that only read public state. This type indicates that no proof generation is needed and the transaction can proceed without one.

### ProofData

The `ProofData` type is the internal representation of proof data within the proof server. It includes the raw cryptographic elements of the proof, the constraint satisfaction witness, and the public input values. This type is not typically exposed to dApps.

### PartialProofData

The `PartialProofData` type represents a proof that has been partially generated. This can occur in recursive proof systems where proofs are built incrementally. It contains the proof data generated so far and instructions for completing the proof.

## Key Material

### Proving Keys

Proving keys are cryptographic material used by the proof server to generate proofs. Each version of a Compact contract has a unique proving key. The proving key is derived from the contract's ZKIR artifact and must be kept secure because its compromise could allow an attacker to generate fraudulent proofs.

Proving keys are stored in the proof server's key store. The key store is typically a directory on disk that contains key files organized by contract address and version. The proof server loads keys on demand when a proof is requested for a contract.

### Verifier Keys

Verifier keys are the public counterpart to proving keys. They are published on-chain when a contract is deployed or upgraded. Validators use verifier keys to check that proofs submitted with transactions are valid. Verifier keys do not need to be kept secret.

The verifier key hash is included in every proof. This hash links the proof to a specific proving key version. When a transaction is submitted, the network checks that the verifier key hash matches the on-chain verifier key for the contract version.

### ZKIR

ZKIR stands for Zero-Knowledge Intermediate Representation. It is a compiled form of the Compact contract that the proof server uses to generate proofs. The ZKIR is produced by the Compact compiler during contract compilation. It contains the arithmetic circuit, constraint system, and type information.

ZKIR artifacts are versioned alongside the contract. When a contract is upgraded, a new ZKIR is compiled. The proof server must have the ZKIR for the exact version of the contract being called. Version mismatches result in proof generation failures.

### Key Versioning

Key versioning ensures that proofs are generated with the correct keys for the contract version being called. Each contract deployment and upgrade produces a new key version. The key version is embedded in the proving key, the verifier key, and the serialized proof.

When a dApp generates a proof, it must use the key version that matches the contract version on-chain. If the contract has been upgraded since the dApp last generated a proof, it must use the new key version. The proof server manages key versions and automatically selects the correct key based on the contract address and the on-chain version.

### Key Rotation

Key rotation is the process of generating new proving and verifier keys. This occurs when a contract is upgraded. The old keys are retired and new keys are used for future proofs. The proof server must support both old and new keys during a transition period to handle transactions that were submitted with the old key version.

The key rotation process for proof servers involves downloading new ZKIR artifacts for the upgraded contract, generating new proving keys from the new ZKIR, verifying that the new verifier key matches the on-chain verifier key, and marking old keys for retirement after a grace period.

## Proof Providers

### httpClientProofProvider

The `httpClientProofProvider` creates a proof provider that communicates with the proof server over HTTP. This provider is used in Node.js environments where direct HTTP access to the proof server is available.

```typescript
import { httpClientProofProvider } from "midnight-js"

const provider = httpClientProofProvider({
  baseUrl: "http://localhost:6300",
  timeout: 30000
})
```

This provider sends proof generation requests to the proof server's HTTP endpoint and returns the results. It handles request serialization, response parsing, error handling, and timeout management. It is the most common proof provider for backend and CLI applications.

### httpClientProvingProvider

The `httpClientProvingProvider` extends the basic proof provider with transaction-aware proving capabilities. It can generate proofs that include transaction context such as nonce and fee information.

```typescript
import { httpClientProvingProvider } from "midnight-js"

const provider = httpClientProvingProvider({
  baseUrl: "http://localhost:6300",
  timeout: 30000
})
```

This provider integrates with the transaction pipeline to ensure that proofs include all necessary context for transaction validation. It is the recommended provider for applications that submit transactions programmatically.

### dappConnectorProofProvider

The `dappConnectorProofProvider` creates a proof provider that works through the DApp Connector. This provider is used in browser environments where the dApp communicates with the proof server through the browser extension wallet.

```typescript
import { dappConnectorProofProvider } from "midnight-js"

const provider = dappConnectorProofProvider(window.midnight)
```

This provider routes proof generation requests through the DApp Connector API. The browser wallet handles communication with the proof server, key management, and session handling. This is the recommended provider for browser-based dApps.

### dappConnectorProvingProvider

The `dappConnectorProvingProvider` combines the DApp Connector integration with transaction-aware proving. It provides the same capabilities as `httpClientProvingProvider` but through the browser wallet interface.

```typescript
import { dappConnectorProvingProvider } from "midnight-js"

const provider = dappConnectorProvingProvider(window.midnight)
```

This is the recommended provider for browser-based dApps that need to submit transactions with proofs.

## Configuration

### Proof Server URL

The proof server URL is the HTTP endpoint where the proof server listens for requests. For local development, the default is `http://localhost:6300`. For test networks, the URL is provided by the network operator. For mainnet, it is typically `https://proof-server.mainnet.midnight.network`.

### Timeout Settings

Proof generation can take several seconds to minutes depending on contract complexity. The timeout setting controls how long the proof provider waits for a response before timing out. The default timeout is 60 seconds. Complex contracts may require longer timeouts. The timeout can be configured per request or globally.

### DEFAULT_CONFIG

The `DEFAULT_CONFIG` object provides default values for proof server configuration. It includes the default proof server URL, the default timeout value, the default retry count, and the default retry delay. Applications can override these defaults with their own configuration.

```typescript
const config = {
  ...DEFAULT_CONFIG,
  baseUrl: "http://my-proof-server:6300",
  timeout: 120000
}
```

### DEFAULT_TIMEOUT

The `DEFAULT_TIMEOUT` constant defines the default timeout value of 60000 milliseconds or 60 seconds. This value balances responsiveness with giving the proof server enough time to complete proof generation for typical contracts. Applications should increase this value when working with complex contracts.

### ProvingProviderConfig

The `ProvingProviderConfig` type defines the full configuration shape for a proof provider. It includes the `baseUrl` for the proof server, the `timeout` for request timeouts, the `retries` count for automatic retries, the `retryDelay` between retry attempts, the `headers` for custom HTTP headers, and the `fetchOptions` for customizing the HTTP client.

## Docker Deployment

### StaticProofServerContainer

The `StaticProofServerContainer` is a Docker container that runs a proof server with a fixed set of contracts. The contracts and their ZKIR artifacts are baked into the container image at build time. This approach is suitable for development environments where the contract set is known in advance.

The static container is configured with the contract addresses and ZKIR files. At startup, it loads all specified contracts, generates proving keys if they do not exist, and begins listening for proof generation requests. The static container does not support adding new contracts at runtime.

### DynamicProofServerContainer

The `DynamicProofServerContainer` is a Docker container that can load contracts at runtime. It accepts API requests to add new contracts and their ZKIR artifacts. This approach is suitable for environments where the contract set changes frequently, such as during development.

The dynamic container starts with no contracts loaded. Contracts are added through the configuration API. The container generates proving keys on demand when a contract is first used. This provides flexibility at the cost of slightly higher latency for the first proof generation request for each contract.

### Container Configuration

Both container types accept configuration through environment variables. Key variables include `PROOF_SERVER_PORT` for the HTTP port, `KEY_STORE_PATH` for the proving key storage location, `LOG_LEVEL` for logging verbosity, and `MAX_CONCURRENT_PROOFS` for limiting concurrent proof generation to avoid resource exhaustion.

### Docker Compose

The proof server is typically deployed as part of a Docker Compose stack alongside the Midnight node and indexer. The Compose file defines the proof server service with its image, ports, volumes for key storage, and environment variables. Health checks ensure the proof server is ready before dependent services start.

A typical Docker Compose service definition for the proof server includes port mapping from 6300 to the container, volume mounts for the key store and ZKIR artifacts, environment variables for configuration, and resource limits for CPU and memory.

## Local Development

### Local Proof Server Setup

Setting up a local proof server involves pulling the proof server Docker image, configuring the container with the appropriate environment variables, mounting the ZKIR artifacts directory, and starting the container. The proof server will then be available at `http://localhost:6300`.

The midnight-local-dev tool automates this setup. Running `midnight-local-dev start` starts a complete local development environment including the proof server. Manual setup is also possible for advanced use cases.

### midnight-local-dev Integration

The midnight-local-dev tool integrates the proof server into the local development environment. It configures the proof server with the correct network settings for the local devnet, ensures the proof server has access to the compiled ZKIR artifacts for deployed contracts, manages the proving key store across restarts, and provides health check integration.

When using midnight-local-dev, the proof server is started automatically. The dApp can connect to it at the configured URL without additional setup. This is the recommended approach for local development.

### Manual Container Management

For manual container management, use Docker commands directly. Pull the proof server image with `docker pull midnight/proof-server:latest`. Run the container with the appropriate configuration. Check the container logs for startup issues. Use Docker commands to stop, restart, or remove the container as needed.

Manual management gives more control over the proof server's configuration but requires more knowledge of the proof server's internals. It is recommended for production deployments and for debugging complex issues.

## Proof Server Errors

### Error Codes

The proof server returns structured error responses with specific error codes. Common error codes include `CIRCUIT_NOT_FOUND` when the ZKIR for the requested contract is not available, `WITNESS_INVALID` when the witness data does not match the circuit's expected inputs, `PROVING_KEY_MISSING` when the proving key for the contract version has not been generated, `PROOF_TIMEOUT` when proof generation exceeds the configured timeout, `RATE_LIMITED` when too many requests are sent in a short period, and `INTERNAL_ERROR` when the proof server encounters an unexpected error.

### Troubleshooting

For `CIRCUIT_NOT_FOUND` errors, verify that the ZKIR artifact is available in the proof server's key store. For `WITNESS_INVALID` errors, check that the witness data matches the contract's expected input types. For `PROVING_KEY_MISSING` errors, trigger key generation by sending a proof request for the contract. For `PROOF_TIMEOUT` errors, increase the timeout or optimize the contract's circuit complexity. For `RATE_LIMITED` errors, implement backoff and reduce request frequency.

### Timeout Handling

Timeout handling follows a specific strategy. The dApp should catch timeout errors and increase the timeout for subsequent retries. For asynchronous proof generation, use the status endpoint to check progress rather than waiting for a response. For contracts that consistently time out, consider architectural changes to reduce circuit complexity.

### Retry Strategies

Retry strategies for proof generation depend on the error type. For transient errors like `INTERNAL_ERROR`, retry with exponential backoff. For `RATE_LIMITED`, wait the specified retry period before trying again. For `CIRCUIT_NOT_FOUND` or `WITNESS_INVALID`, do not retry because these errors indicate a configuration problem. For `PROOF_TIMEOUT`, retry with a longer timeout.

## Performance Tuning

### Concurrent Proof Generation

The proof server can handle multiple proof generation requests concurrently. The degree of concurrency is limited by the server's CPU and memory resources. Each proof generation is CPU intensive and memory hungry. Increasing concurrency beyond the server's capacity degrades performance for all requests.

Configure the maximum concurrent proofs based on the server's CPU count. A good starting point is one concurrent proof per CPU core minus one core reserved for system operations. Monitor CPU and memory usage to find the optimal setting.

### Resource Allocation

The proof server benefits from fast CPUs with high clock speeds and memory with high bandwidth. Proof generation is primarily CPU bound. GPU acceleration is available for some proving systems and can significantly reduce proof generation time. Memory requirements depend on the complexity of the contract's circuit. Complex circuits with many constraints require more memory.

Allocate at least 2 CPU cores and 4 GB of memory for development environments. Production environments should allocate at least 4 CPU cores and 8 GB of memory. Contracts with very complex circuits may require more resources.

### Caching Strategies

The proof server caches loaded ZKIR artifacts and generated proving keys to avoid redundant work. The cache is typically in-memory with a configurable size limit. When the cache is full, least recently used items are evicted.

For frequently called contracts, pre-load their ZKIR artifacts and pre-generate their proving keys. This ensures that proof generation requests for these contracts do not experience the latency of loading artifacts and generating keys on demand.

### GPU Acceleration

GPU acceleration can significantly reduce proof generation time for complex circuits. The proof server supports GPU acceleration through CUDA or OpenCL backends. Enable GPU acceleration in the proof server configuration if compatible hardware is available. Not all proving systems support GPU acceleration.

## Operational Monitoring

### Health Checks

The proof server exposes a `/health` endpoint that returns a 200 status when healthy. The health check verifies that the proof server process is running, the key store is accessible, and required dependencies are available.

### Metrics Collection

The proof server exposes a `/metrics` endpoint with Prometheus-compatible metrics. Key metrics include `proof_requests_total` for the total number of proof generation requests, `proof_generation_duration_seconds` for proof generation time distribution, `proof_errors_total` for error count by error type, `active_proofs` for the current number of active proof generations, and `cache_hit_ratio` for the cache effectiveness.

### Log Analysis

The proof server logs key events including proof generation start and completion, error occurrences with details, key generation and loading, and health check results. Log levels can be configured to control verbosity. In production, aggregate logs into a centralized logging system for analysis and alerting.

### Alert Configuration

Configure alerts for proof generation error rate exceeding a threshold, proof generation latency exceeding a percentile threshold, queue depth exceeding the maximum concurrent proofs setting, and health check failures.

## Integration Patterns

### submitCallTx Flow

When submitting a contract call transaction, the proof generation flow is as follows. First the dApp prepares the witness data from the user's wallet. Second it sends the witness to the proof server for proof generation. Third it receives the serialized proof. Fourth it constructs the transaction with the proof included. Fifth it submits the transaction to the network.

The `submitCallTx` function handles this flow automatically when configured with a proof provider. The dApp does not need to manage the proof generation step directly. The proof provider is invoked internally during transaction construction.

### submitDeployTx Flow

Contract deployment also requires proof generation. The deployment proof attests that the contract is being deployed correctly. The flow is similar to `submitCallTx` but the witness data includes the contract's initial state rather than method call inputs.

### submitTx Flow

The `submitTx` function handles the general transaction submission flow including proof generation. It is used for transactions that are not specifically contract calls or deployments, such as DUST transfers or unshielded token transfers.

### submitTxAsync Flow

The `submitTxAsync` function submits a transaction asynchronously and returns a transaction ID immediately. Proof generation and transaction construction happen in the background. The dApp can check the transaction status later. This is useful for transactions that may take a long time due to complex proof generation.

## Proof Erasure

### ProofErasedTransaction

The `ProofErasedTransaction` type represents a transaction where the proof has been erased after submission. This occurs in proof-less transaction flows where the proof is not needed after the transaction is included in a block. The proof is stripped from the transaction to reduce storage requirements.

### ProofErasedInput

The `ProofErasedInput` type represents an input to a proof-erased transaction. It contains the input data without the associated proof. This type is used when reconstructing transaction history from on-chain data where proofs have been removed.

### ProofErasedOutput

The `ProofErasedOutput` type represents an output of a proof-erased transaction. Similar to `ProofErasedInput`, it contains output data without proof information.

### ProofErasedOffer

The `ProofErasedOffer` type represents a ZSwap offer in a proof-erased context. It contains offer data stripped of proof information.

### Proof less Transactions

Some transactions do not require proofs at all. These include system transactions such as epoch transitions, unshielded token transfers that do not interact with Compact contracts, and DUST generation and consumption events. The proof server is not involved in these transactions and the `NoProof` type is used to indicate that no proof is needed.

## Best Practices

### Proving Strategy

Pre-generate proofs for common contract calls to reduce user wait time. Cache generated proofs when the same witness data is used frequently. Use asynchronous proof generation for complex proofs so the user interface remains responsive. Monitor proof generation times and optimize contracts with slow proving times.

### Error Recovery

Implement graceful degradation when the proof server is unavailable. Cache previously generated proofs locally for offline use. Provide clear error messages to users when proof generation fails. Log proof generation errors with enough detail to diagnose issues.

### Timeout Management

Set timeouts based on contract complexity. Simple contracts may prove in under 5 seconds. Medium complexity contracts may take 10 to 30 seconds. Complex contracts may take 1 to 5 minutes. Set timeouts accordingly and communicate expected wait times to users.

### Key Material Lifecycle

Keep proving keys synchronized with on-chain contract versions. Regenerate proving keys after contract upgrades. Archive old proving keys in case they are needed for historical data access. Secure proving keys because their compromise could allow fraudulent proof generation.

## Compatibility

### Proof Server Versions

The proof server has its own versioning independent of other Midnight components. Version X of the proof server may not be compatible with version Y of the Compact runtime or ledger. Always check the compatibility matrix for the specific versions you are using.

### Ledger Versions

The proof server must be compatible with the ledger version it is generating proofs for. The ledger version determines the proof format and verification algorithm. Proofs generated for one ledger version may not be valid on another. The midnight-local-dev tool ensures version compatibility in the local environment.

### Compact Runtime Versions

The Compact runtime version used by the proof server must match the runtime version used by the network. The runtime determines how circuits are executed and how proofs are generated. Mismatches cause proof verification failures.

### ZSwap Versions

If your dApp uses ZSwap shielded token swaps, the proof server must support the ZSwap version in use. ZSwap has its own versioning that is independent of the main proof server version.
